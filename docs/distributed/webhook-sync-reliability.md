## 问题

系统 A 的数据要准实时同步到系统 B，用 Webhook 做增量通知。现实是：Webhook 会重复推送、服务重启期间事件会丢、对端还会限流拒绝写入。
怎么设计这条同步链路，才能保证两边最终一致？（简历项目：Teambition → 钉钉 AI 表格的同步引擎）

## 核心答案

- **三段式架构**：Webhook 回调只做轻量解析 + 入队（绝不在回调里调外部 API，防止回调超时）→ 后台线程按批次拉取详情并 upsert 目标系统 → 每日低峰执行一次全量校准兜底。

- **不重（去重）**：按事件 ID 落库去重；同一实体多次变更按实体 ID 合并、只保留最新状态；**去重标记与任务入队放在同一个数据库事务里**，杜绝"事件已处理但任务没入队"的窗口。

- **不丢（重试 + 死信 + 对账）**：失败任务指数退避重试（如 60s → 3600s，最多 8 次），超限转入**死信队列**不再阻塞后续任务，修复诱因后可人工重放；每日全量校准周期性对齐两边状态，把增量阶段任何丢失和乱序修正回来——**增量管快，全量管对**。

- **幂等写入**：按业务主键 upsert；发现目标表存在重复主键时直接拒绝写入并告警（防止更新错行）。

- **可观测**：每条写入结果落 JSONL 日志（成功 / 跳过字段及原因 / 错误摘要），健康检查接口暴露待同步队列、等待队列、死信队列计数。

## 深度解析

- 追问点：为什么回调里不直接写目标系统？——Webhook 有超时窗口，处理慢了会被对端禁用回调；入队-批处理还天然削峰，让对端限流可控。

- 追问点：目标平台有限制（如同步表禁止第三方直接新增行）怎么办？——**等待行轮询模式**：任务留在等待队列，按固定间隔重查目标行是否出现；等待期不计入失败次数（不是任务的错），超过等待上限才转死信，避免无限堆积。

- 追问点：这套机制和 MQ 可靠性方案什么关系？——语义同构：事件 ID 去重 = 消费幂等；重试 + 死信 = MQ 的重试队列与 DLQ；全量校准 = 对账补偿。Webhook + SQLite 队列是轻量级实现，吞吐或并发上来后平滑替换成 MQ，机制设计不变。

- 安全配套：回调必须验签（HMAC 签名 / HS256 JWT）防伪造、限制请求体大小、调试接口默认关闭且走独立 Token 鉴权。
