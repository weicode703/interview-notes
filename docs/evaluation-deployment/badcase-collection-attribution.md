## 问题

线上 badcase 从哪来？怎么定位是哪个环节出的问题？收完之后怎么迭代、怎么防止回退？

## 核心答案

**一、三个来源**

- 用户侧：重新生成按钮、差评、客服工单；
- 系统侧：日志全量落盘，按规则自动捞——无答案回复、超时、工具调用失败、空检索；
- 主动侧：抽样人工标注、LLM 自动质检打分。

**二、归因：找第一个出错环节，不看最终答案**

最终答案错了，往往是上游连锁反应的结果。三条手段：

1. **Trace 回放**：每一步的 Thought / Action / Observation、召回列表、工具出入参全部落盘，沿轨迹找 **first error**；
2. **黄金输入注入（控制变量）**：把正确的检索结果直接喂给生成模型——答对了，问题在检索；还答错，问题在生成。把正确的工具和参数直接注入执行——成功了，问题在规划/选工具；失败了，问题在工具或环境；
3. **分层排除**：模型 → Prompt → 检索 → 工具 → 数据，每层看自己的日志，时间线对齐。

**三、迭代闭环**

归因出的问题要落到具体修复动作（改 prompt / 改检索策略 / 改工具描述 / 加确定性规则），每条 badcase 进回归集，改完跑回归防止回退。

## 深度解析

- **别只看 badcase 数量，要看按环节的分布**：如果大部分集中在检索召回，那优化生成模型就是浪费；这也是「小层面提优、大方向负优化」的防法。
- **控制变量法为什么好用**：它把「多环节耦合」拆成「单环节验证」，一次注入就能排除一半可能性，比逐层猜快得多。
- **和 trace 的关系**：没有全链路 trace，归因只能靠猜；所以 tracing 不是运维锦上添花，是做 badcase 归因的前提。
