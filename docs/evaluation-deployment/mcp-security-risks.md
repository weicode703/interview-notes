## 问题

接了 MCP 之后攻击面变大在哪？提示词注入、权限过大、恶意 server、数据外泄分别怎么防？什么操作必须让人确认、什么可以静默放行？

## 核心答案

**五类风险 + 对策**：

1. **提示词注入**：工具返回的内容里藏恶意指令（网页、文件、接口回包都可能）。对策：**工具结果只当数据、不当指令**；结果里出现「忽略之前的指令」这类模式要剥离或标注；敏感动作前再做一次校验和确认。
2. **权限过大**：工具拿到的权限超过实际需要。对策：权限最小化，能读就别给写，按**工具粒度**授权而不是按账号粒度。
3. **恶意 / 不可信 server**：第三方 server 偷数据、返回毒内容。对策：只用可信来源、固定版本；外来 server 隔离运行（容器/沙箱），限制它能碰的文件和网络；记录并审计它的调用。
4. **数据外泄**：敏感数据被工具发出去。对策：出口管控 + 脱敏，敏感字段不传、传前审计，日志同样脱敏。
5. **敏感操作无确认**：删除、支付、发消息直接执行。对策：高风险操作强制人工确认。

**审批边界**（可以直接背）：

- **必须确认**：删除/覆盖、支付转账、对外发消息（邮件、IM）、改配置、执行代码或命令、授权与凭证变更；
- **可以静默**：纯读操作——查文件、搜资料、只读查询。但只读也要防「读到不该读的」：路径围栏、行级/租户级权限。

## 深度解析

- **审批怎么实现**：给工具声明 `needs_approval`，命中时挂起（state 落库、释放执行资源），把待审批调用列给用户，approve / reject 后从断点恢复执行。
- **怎么少打扰**：记住已授权的范围（同一工具同类参数不再问）、按规则批量放行（如「只读全部放行」）、把多次待审批合并成一次展示。全都问一遍，用户会关掉审批。
- **最容易被忽略的一条**：注入不一定来自「用户说的」，多数来自「工具读回来的」。所以防注入的重点在**数据入口**，不在输入框。
