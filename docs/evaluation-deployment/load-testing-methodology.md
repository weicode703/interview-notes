## 问题

系统上线前怎么验证能扛多少流量？QPS、TPS、RT、并发数是什么关系？
用什么工具、怎么设计压测方案、怎么找到系统的容量水位？

## 核心答案

- **先把指标说清楚**：
  - **QPS/TPS**：每秒查询/事务数（吞吐）；**RT**：单请求耗时（看 P95/P99 而不是平均值——长尾才是用户感受）；
  - **并发数**：同时在途的请求数。三者关系：**并发数 ≈ QPS × 平均 RT**（Little 定律）——想扛 1000 QPS、RT 100ms，并发容量就是 100。

- **工具三选**：**wrk**（轻量 HTTP，命令行秒起，适合接口基准）、**JMeter**（图形化、协议全、报表全，适合复杂场景）、**Locust**（Python 写脚本、可模拟业务逻辑，适合写"用户行为"模型）。

- **压测方法（阶梯加压找水位）**：从低并发开始，每档稳压几分钟，逐级加压（100→200→400→800…），画"压力-RT/QPS"曲线——**QPS 拐点 + RT 陡升的位置就是容量水位**；水位取拐点的 70-80% 作为安全容量，留突发余量。

- **压测的三种类型**：基准压测（单接口容量）、**混合场景**（按线上流量比例模拟真实业务流）、**浸泡测试**（长时间中压跑，抓内存泄漏/连接泄漏）——只测单接口会高估容量。

## 深度解析

- 追问点：压测结果和线上不符的常见原因？——压测机自身先到瓶颈（本机 CPU/端口/带宽）、流量模型失真（没有慢查询比例）、数据量失真（库里 1 万行 vs 线上 1000 万行的索引行为）、缓存被"预热"得太理想。

- 追问点：压测中 RT 上升但 QPS 还没到拐点，先看什么？——**各池的排队情况**：DB 连接等待、线程池队列、下游限流——排队是吞吐未满但延迟先涨的主因（对应"池是排队而非并行"）。

- 追问点：压 LLM 应用有什么特别之处？——上游 API 限流是天花板（压自己会被上游 429 反噬），要 mock 上游测自身容量，单独压真实上游前先确认配额；SSE 长连接压的是并发连接数而非 QPS。

- 常见误区：拿平均值汇报 RT——平均 50ms 可能 P99 是 3 秒；性能报告永远用分位数（P50/P95/P99）。
