## 问题

多用户场景下 MCP 怎么部署？一个 MCP server 进程同时只能处理一个工具调用，Agent 要并发调多个工具怎么办，连接池怎么设计？server 挂了怎么处理？

## 核心答案

**一、多用户部署：隔离优先**

- 每个用户独立的会话 / 进程 / 凭证，**绝不串**，这是安全底线；
- stdio 模式：每个用户拉起自己的 server 进程，天然隔离，但资源开销大，适合用户量小的场景；
- HTTP 模式：共享服务，靠会话标识区分用户，按用户做限流、权限、数据隔离，适合规模大的场景；
- 凭证管理：每个用户的工具凭证（数据库、API key）分开存、分开用；
- 常见形态：前面放一个网关层统一做鉴权、限流、路由，后面接各 server 实例。

**二、并发：池的对象不一样**

**stdio 用进程池**（每连接串行，池大小换并发）：

1. 池初始化时按 min size 先 spawn N 个 server 子进程；
2. 每个进程依次走完 initialize → 收 capabilities → 发 initialized 通知 → tools/list 拉工具并缓存；
3. 握手全部完成标记为 ready，放进空闲队列；
4. 借出前检查进程是否还活着，死了就丢弃、重新预热一个；
5. **重建连接必须重新走 initialize 握手**，不能直接复用旧状态。

**Streamable HTTP 的池从「进程」变成「会话」**：服务器天然支持并发，不用多开进程。会话管理就是管「标识的创建、复用、过期、关闭」，过期要自动重握手；限流由客户端管并发上限和熔断、服务端管 QPS 和排队；隔离按租户分池分会话，凭证和状态不共享。

**三、server 挂了怎么办**

- **重试**：幂等操作可以重试一两次；有副作用的不能盲目重试，怕重复执行；
- **重建连接**：重连后要重新握手协商，不能直接复用旧状态；
- **降级**：告诉模型「这个工具暂时不可用」，让它换方案或提示用户，而不是整个 agent 崩掉；
- **熔断**：连续失败先停用这个 server，冷却后再探测恢复；
- **兜底**：关键工具做多实例冗余，挂了自动切备用。

## 深度解析

- **为什么 stdio 一定要池**：一个进程一次只处理一个调用，Agent 并发调三个工具就会排队；池化后每个进程仍是串行，但整体并发上去了。
- **最容易忘的一步是探活**：借出前不检查，就会借到一个已经死掉的进程，表现为「莫名其妙超时」，而不是报错。
- **HTTP 模式的隐形问题**：会话过期后没重握手，会出现「前半段正常、后半段全失败」的现象——会话过期要显式处理。
