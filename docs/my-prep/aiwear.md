# AIWear 智能穿搭助手 — 追问准备册

> 简历一句话（与新简历逐字对齐）：面向穿搭场景的多模态 AI 应用——多模态检索链路（Qwen-VL 图片理解 → 本地 CLIP 编码 → Redis 用户级 512 维向量索引，文搜图/图搜图余弦相似度 TopK）；零样本分类＋双路兜底；RAG 三级降级＋五类 SSE 事件协议；JWT＋Redis Token 黑名单认证；Docker Compose 五容器编排部署上云。

## 电梯稿（30 秒，背熟）

> AIWear 是一个穿搭场景的多模态 AI 应用：用户传图，能做 AI 图片编辑合并、文搜图图搜图、穿搭知识库问答。检索链路是 Qwen-VL 做图片理解、本地 CLIP 把图文映射到同一 512 维向量空间、Redis 按用户建索引做 TopK 余弦检索；图搜图前还用 CLIP 文本提示做零样本品类分类先收窄候选。RAG 问答做了三级模型降级和五类 SSE 事件协议做流式。后端 FastAPI + PostgreSQL + Redis，JWT 认证，Docker Compose 五容器编排，已部署在云服务器跑通。

## 高概率追问链（含参考答案）

### 一、CLIP 向量检索（最容易被深挖）

**1. 向量为什么放 Redis，不用 pgvector 或专用向量库？** ⭐3

参考答案（权衡 + 演进的标准答法）：
- **当前选型的理由**：图片量在【填你的数字，如几千到几万】量级，TopK 内存暴力检索毫秒级返回，性能完全够；Redis 本来就在栈里（会话/缓存），向量索引复用它省掉一个新组件，部署和运维成本最低。
- **边界在哪**：Redis 向量检索是内存型的，数据量上到几十万条、内存成本和持久化压力就上来了，而且缺乏复杂过滤（按用户/类目过滤要自己在外层做）。
- **演进路线**：仓库 README 里就写了计划迁移 pgvector——触发条件就是规模：向量条数上十万级或需要带过滤的混合检索时，迁到 PostgreSQL 的 pgvector（数据和应用同库，事务一致性好）。这样答展示的是"我知道每个选择的边界"，而不是"我不知道有更好的方案"。

**2. 检索是 topK 还是 topP？召回质量怎么评？** ⭐2

参考答案：topK（检索场景是取前 K 条给用户看，topP 是生成采样的概念——迅雷面经里这问就是考概念边界）。质量评估：我构造了一个"查询语句 → 正确穿搭图"的小评测集，看 hit@K【填你实际测的数据；没测过就说计划怎么做，别瞎编数字】。

**3. CLIP 用哪个版本？中文查询效果怎么保证？** ⭐2

参考答案：CLIP-ViT-Base-Patch16，输出 **512 维**向量（ViT-B/16 的投影空间）。它双塔结构、用 4 亿图文对做过对比学习预训练，图像和文本天然对齐到同一空间，跨模态检索不需要标注配对数据。局限要主动说：原版 CLIP 的文本塔以英文为主，中文查询效果打折——应对是查询侧做翻译/规范化，或者换 Chinese-CLIP 这类中文对齐的变体（这是已知的演进项）。

**3b. 零样本分类怎么做的？为什么还需要规则兜底？** ⭐3（简历写了"零样本分类＋双路兜底"，必被追问）

参考答案（双路设计）：
- **主路（CLIP 零样本）**：图搜图时，先用几条品类文本提示（"服装单品 商品图…"、"人物头像…"、"人物穿着服装 全身穿搭…"）分别编码成向量，和查询图向量算余弦——得分最高的品类就是查询图的类别，先按品类把候选集从"用户全部图片"收窄到"该品类图片"，检索相关性和比对效率双提升。零样本的意义：**不需要训练任何分类器**，CLIP 的图文对齐能力直接当分类器用。
- **兜底路（规则）**：Redis 里的存量老数据可能没有品类标记——用入库时 Qwen-VL 生成的图片描述跑**品类关键词词典**（裙/衬衫/外套/裤…上百个词）推断品类，兼容历史数据。
- 追问"为什么不全信零样本"：CLIP 中文提示的判别力有限、品类间的边界（人像 vs 穿搭照）本来就有模糊区；规则词典是确定性的、可人工维护的——**概率判断 + 确定性规则双保险**，和智居 Agent 的反幻觉双保险是同一个设计思想。

### 二、RAG 问答

**4. RAG 整条链怎么做的？怎么避免编造？** ⭐2

参考答案：穿搭知识库结构化程度高，按"搭配条目"为粒度切块而不是固定长度硬切；检索双路——关键词保住"阔腿裤"这类精确词，向量兜住"上班穿什么比较得体"这类语义问法；生成时要求答案必须基于召回片段并带上条目来源，前端展示可溯源；召回为空或置信度低就走兜底话术"这个问题我还没学到"。参考 [RAG 项目 10 连问](/rag/rag-project-deep-dive-chain) 对齐追问节奏。

**5. SSE 为什么不用 WebSocket？断线了怎么办？** ⭐2

参考答案：RAG 问答是单向的服务器→用户推送，SSE 够用且更简单——复用 HTTP、自动重连、代理友好；WebSocket 的双向能力在这个场景用不上。断线：EventSource 自带重连，后端按请求无状态生成，重连就是重新生成一次，代价可接受；如果要断点续传再考虑会话级缓存。

### 三、Qwen-VL 多模态

**6. 模型理解错用户意图（改错图）怎么办？** ⭐2

参考答案：把自由文本编辑约束成**参数化操作 + 确认预览**——模型输出结构化的编辑参数（操作类型/区域/风格），前端先展示参数让用户确认再执行，参数解析失败就重试或引导用户换说法。这答的是"约束模型自由度 + 把确认成本放在错误成本之前"。

**7. 图片编辑是同步的吗？涨量了怎么办？** ⭐2

参考答案：当前是同步调用，单次【填你的耗时，如 3-8 秒】；用户量上来后这是最先扛不住的点（同步占死 worker）。演进：改成任务队列异步化——提交返回任务 ID，前端轮询或推送取结果。这是 README 里已列的后续计划，照实讲。

### 四、后端与部署

**8. JWT + Redis 黑名单怎么设计的？token 泄露怎么办？** ⭐2

参考答案：登录发 JWT（带过期时间和 jti 唯一标识）；登出/修改密码时把该 token 的 jti 写入 Redis 黑名单，TTL 设成 token 剩余有效期（到期自动清理，不占内存）；每次请求校验签名后查黑名单。泄露处置：让用户改密 + 该用户所有会话强制下线（按用户维度清发oken）。

**9. Docker Compose 编排了什么？Nginx 干嘛的？** ⭐1

参考答案：FastAPI 应用、PostgreSQL、Redis、Nginx 四个服务；Nginx 做反向代理和静态资源托管（前端产物），并把请求转发给 FastAPI，应用容器不直接对外暴露端口。

### 五、场景设计变体

**10. 用户量涨 10 倍，最先崩哪？** ⭐3

参考答案（按层推演，对标字节场景题答法）：第一崩的是 **VL 接口**——同步调用 3-8 秒占死 worker，并发一上来队列堆积（→ 异步任务化）；第二是 **CLIP 向量规模**（→ pgvector 迁移）；第三是 **SSE 长连接数**占网关连接（→ 调整超时/连接复用）。有优先级的推演比罗列所有问题更能得分。

## 踩坑实录：SSE 流式输出变成"一次性返回"（真实 bug，面试直接讲）

**现象**：前端应该逐字出现回答，实际等几秒后整段一次性蹦出来。

**排查过程（分层二分，这个方法论是面试官想听的）**：
1. 先确认 LLM 层没撒谎——DashScope 调用参数里 `stream=True, incremental_output=True` 是开着的；用 `curl -N` 直接打后端 SSE 接口，逐块到达 = 后端没问题；
2. 问题锁定中间层：Docker Compose 里的 **Nginx 反代默认 `proxy_buffering on`**，会把上游响应攒满缓冲区再转发——SSE 的几十个 chunk 被攒成一坨一次性下发，这就是"全给我"的直接原因；
3. **修复**：nginx location 加 `proxy_buffering off; gzip off;`（gzip 压缩也会攒缓冲），应用侧响应头加 `X-Accel-Buffering: no` + `Cache-Control: no-cache` 双保险——反代见到这个头会自动关闭缓冲；
4. **第二个隐藏坑**：DashScope SDK 不同版本的流式返回格式不同——有的返回**累积全文**、有的返回**增量**，按增量处理就显示错乱。修复：后端用前缀比对统一归一化成增量（`text.startswith(previous_text)` 则裁掉前缀），前端也做了 startsWith 兼容。

**面试总结句**：SSE 链路上每一层（LLM SDK → 应用 → 反代 → 浏览器）都可能缓冲，排查用 `curl -N` 逐层二分，修复要在应用响应头和反代配置双侧落地。

**代码审视发现的隐患（主动说出来是加分项）**：`stream_chat_answer` 里 `except Exception: pass` 会**静默吞掉**模型异常并降级到"假流式"（整段检索文案切 8 字符块模拟流式）——用户毫无感知地拿到降级答案；且如果流到一半才失败，会先吐半截真答案、再补整段 fallback，内容重复。改进方向：至少记日志 + 只在"尚未产出任何内容"时才降级。SSE 事件里的 `source` 字段（qwen / fallback）就是用来现场验证走了哪条路的。

## 源码级追问（面试官读过你代码才会问的）

**11. SSE 事件为什么分 start / progress / delta / done 四种类型？**

参考答案：这是首字延迟优化——`start` 事件在检索开始前就发出（带会话 ID），前端立刻进入"思考中"状态；`progress` 报告"正在检索知识库"；等检索和首 token 都好了才开始 `delta`。如果只有一个事件类型，用户要干等检索 + 生成全部完成，体验差一个量级。

**12. 为什么前端用 fetch + ReadableStream 而不是 EventSource？**

参考答案：**EventSource 只支持 GET 请求**，没法带 JSON body 和 Authorization 头——RAG 聊天是 POST 且需要认证，所以用 fetch 读流手动解析 SSE 格式。这是选型的硬理由，不是不知道 EventSource。

**13. 为什么后端把 LLM 的 chunk 再切成 4 字符 + sleep(0.015)？**

参考答案（诚实答法）：为了统一不同模型供应商的输出节奏，让前端渲染节奏稳定。但我要主动指出这个设计的代价：它人为节流了真流式的速度（~260 字/秒），网络层再快展示层也封顶在这个速度；更好的做法是把节奏控制完全交给前端打字机层，后端拿到多少推多少。能指出自己代码的改进点，比掩饰更加分。

**14. 模型调用有降级策略吗？**

参考答案：三级——DashScope 流式（主）→ OpenAI 兼容接口流式（备，换 base_url 即接其他供应商）→ 检索结果拼接的本地兜底答案（保底，保证接口永远有输出）。代价和隐患见上面的"代码审视"。

## 危险区

- 数字空窟窿：图片量级、单次 VL 耗时、检索延迟——面试前把三个数填进上面答案
- "每步都是调 API"的质疑：准备一个你亲手处理的边界 case（如 VL 返回格式偶发解析失败的重试逻辑）
- RAG 没有评测集：哪怕 10 条人工核对过的问答对，也说得出方法
