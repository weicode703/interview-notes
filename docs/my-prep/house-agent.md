# 智居 Agent（房源推荐与预约）— 追问准备册

> 简历一句话（与新简历逐字对齐）：基于 LangGraph 的"单入口、多子图"租房 Agent——主图级 Human-in-the-loop 网关（additional_kwargs 消息协议上浮 interrupt）；反幻觉双保险（LLM 结构化抽取 8 个需求字段＋正则强校验，未明确说出的字段一律丢弃）；SQL Agent 审核节（get_schema → generate → check → run，推荐结果 100% 来自真实数据库查询）；LangGraph Store 持久化偏好与预约，预约标题强制命中会话推荐结果，流程结束自动清空状态。
> 仓库：github.com/saojesus733-gif/house-agent

## 电梯稿（30 秒，背熟）

> 租房这个场景对话轮次多、要跨会话，普通聊天机器人做不到"记住你、断掉了还能续"。我用 LangGraph 做了一个多子图 Agent：主图做意图路由，推荐、预约、闲聊各是一个子图；需求没说全会用 interrupt 暂停下来收集参数，状态全部 checkpoint 到 PostgreSQL，用户三天后回来还能接着聊；房源查询用 LLM 生成 SQL，程序侧校验后执行。整条链路从需求补全到预约看房是业务闭环。

## 高概率追问链（含参考答案）

### 一、架构选型（必问）

**1. 为什么拆推荐子图和预约子图？单图不行吗？ReAct 和状态机怎么区分？** ⭐3

参考答案：拆分是因为两个子任务的状态结构和流程完全不同——推荐子图围绕"查询条件→检索→排序"，预约子图围绕"信息收集→校验→出工单"，混在一个图里 state 会膨胀、条件边爆炸。关于 ReAct 和状态机：租房场景的路径是**可枚举的**（就是那几个步骤），所以用图编排确定性流程，LLM 只在节点内部做总结和生成，可控且省 token；ReAct 适合路径不可预知的开放任务。如果面试官说"这其实就是工作流"——**承认并深化**：对，推荐子图本质是工作流，我刻意把确定性放在代码里，只把语言理解交给模型，这是设计而非局限。

### 二、Interrupt 中断恢复（王牌，必须讲透）

**2. interrupt 的原理是什么？状态存在哪？断线重连怎么续上？** ⭐3

参考答案（三段式）：
- **为什么需要**：需求补全要用户输入。没有持久化，用户填到一半关页面，会话就死了；有了 checkpoint，对话是可以"暂停再续"的。
- **机制**：LangGraph 每个节点执行完都会把整条线程的 state checkpoint 写入 PostgreSQL（PostgresSaver）。执行到 `interrupt()` 时，图在这个节点暂停，把要收集的信息（表单结构）抛给前端，线程停在断点；用户提交后用 `Command(resume=表单值)` 恢复执行，暂停节点直接拿到值继续跑。恢复不是"重放历史"，是**从 checkpoint 里加载状态后从断点继续**。
- **断线/三天后回来**：前端凭 thread_id 拉线程当前状态，发现处于 interrupt 中断点就重新渲染那张表单；checkpoint 在库里，随时可续。

追问"和自定义 state 字段管理多轮会话比，为什么两个都用"：state 字段管的是**业务内**的多轮（比如用户改预算），interrupt 管的是**跨等待**的中断（要用户人在场输入）——粒度不同，配合使用。

### 三、SQL 生成与校验（简历写了"生成并校验"，必被追问）

**3. 生成的 SQL 怎么校验？查询错了怎么兜底？** ⭐3

参考答案（按你的真实实现讲）：查询链路用的是 LangChain 的 SQL 工具链（`SQLDatabaseToolkit`），子图节点流是 list_tables → get_schema 拿表结构 → generate_query 生成 → **check_query 用 LLM 审核节复查** → run_query 执行。审核节专盯 SQL 常见错误：**NOT IN 遇 NULL 的语义陷阱、JOIN 条件错误、类型不匹配、BETWEEN 边界误用**——有问题改写后再放行执行。防护再叠三层：数据库账号**只读**（注入了也写不进去）；prompt 明确禁止 INSERT/UPDATE/DELETE/DROP；提取用户条件用 `with_structured_output` 结构化输出（城市/预算/房型是类型化字段），不让模型自由发挥拼 SQL。一句总纲（简历原话）：**推荐结果 100% 来自真实数据库查询**——房源数据只能来自库里查出来的行，模型只负责把行变成推荐理由，结构上就不可能编造房源。执行报错会把错误信息回传给 LLM 修正重试。追问"准确率"：用【填你的数字】条自测查询量化，讲清评测方法比数字重要。

### 四、意图识别与记忆

**4. 意图路由怎么知道分对了？相似问法不同意图怎么办？** ⭐2

参考答案：路由是 prompt + few-shot 的 LLM 分类；准确率用自测问句集量化【填你的数字】。相似问法不同意图——单靠语义相似度确实分不开，所以要结合**槽位状态**：比如"我想看看别的"在有推荐结果的上下文里是翻页意图，在开场是推荐意图；分不清时用 interrupt 式澄清反问确认，而不是硬猜。

**5. Store 里的偏好，用户回来后按旧的推还是重新问？** ⭐3

参考答案（这是迅雷面试官说他们没解好的开放题，给框架不装懂）：我的做法是偏好作为**候选**注入 prompt，同时**显式确认**——"上次你说预算 3000，还按这个来吗？"核心思路：让确认成本低于猜错成本；偏好带更新时间，过期的不自动用。诚实补充：完全自动判断"该用旧方案还是新方案"没有银弹，确认交互是工程上最稳的解。

### 五、杂项快答

**6. PG 存 LangGraph 状态、MySQL 存业务数据，为什么分开？** — saver 生态 PG 最成熟（官方实现），框架状态和业务数据生命周期不同，分开各自演进互不拖累。

**7. 预约收集手机号/身份证，怎么处理敏感信息？重复下单怎么防？** — 敏感字段只在生成工单时使用、日志不落明文；工单生成后清空会话预约状态，且校验目标房源必须来自当前会话的推荐列表，防重复和防伪造。

**8. 房源表加了新字段（如地铁线），链路哪里要改？** — 只改 prompt 里的 schema 描述和白名单，编排代码零改动——schema 是元数据驱动的。（对标字节场景题"表结构变了怎么处理"）

## 源码级追问（面试官读过你代码才会问的）

**10. 为什么 interrupt 不放在子图里，而是在主图加一个"网关节点"（gateway）？**

参考答案（你的真实设计）：子图保持纯业务逻辑（检索、筛选、生成），人机交互统一收敛到主图的 `recommend_input_gateway` / `reserve_input_gateway` 两个网关节点——子图通过消息的 `additional_kwargs` 携带结构化请求（`{"field", "question"}`），网关节点检测到请求就 `interrupt()` 暂停。好处有三：人机交互的协议只有一处实现；子图不用感知"自己跑在什么宿主环境"；答案回来后网关把输入规范化成带结构化标记的 HumanMessage 注回消息流，子图拿到的是干净的输入。

**11. 用户提交空答案怎么办？**

参考答案：网关里做了**重问机制**——resume 回来的值为空，就再发一次 `interrupt({"question": "...（不能为空）"})`。原理：每次 resume 后该节点从头重新执行，第一个 interrupt 直接取到提交值，空则走到第二个 interrupt 再次暂停等待——用顺序 interrupt 实现了简单校验循环，不需要额外状态。

**12. 子图和主图之间为什么用消息的 additional_kwargs 传数据，不共享 state 字段？**

参考答案：LangGraph 子图有独立的状态 schema，主图和子图直接共享字段会让两层 schema 耦合；用消息通道携带结构化载荷，子图对主图的输出协议就是"消息 + 附加标记"，边界清晰、各自演进。代价是要多写一层 gateway 的编解码——权衡后值得。

**13. 需求补全是靠 LLM 自由发挥吗？反幻觉双保险具体怎么落？**（简历原话：LLM 结构化抽取 8 个需求字段后叠加正则强校验）

参考答案（双保险，缺一不可）：
- **第一保（结构化）**：信息提取用 `with_structured_output(schema=UserInfo)` 强制结构化——城市、区域、预算上下限、户型、朝向、推荐数量等 **8 个字段**全部类型化，LLM 只能填槽不能自由发挥；缺省字段有默认值兜底（用户说"不提供"就走默认条件）。
- **第二保（正则强校验）**：**模型说抽到了不算，用户原话里命中才算**——城市字段必须命中常见城市名或"市/区/县"后缀的正则；预算必须命中"数字＋元/k/千"的金额模式；"以上/以下"这类方向词用来消除区间歧义（说"3000 以下"就清掉下限）。原话里没有的，抽取结果直接丢弃置空。
- **为什么两道都要**：只靠结构化输出，模型会"礼貌地编"（用户没说城市它猜一个）；只靠正则没法理解自然语言。**LLM 管理解、正则管事实**——这个"概率输出＋确定性校验"的思想和 AIWear 的零样本分类＋规则兜底同源，可以互相印证。

## 危险区

- interrupt 被追"重启服务后线程还在吗"——在，checkpoint 落库了，和代码部署无关
- 说不出 Text2SQL 的评测方法——准备一个 30 条左右的自测集口径
- 三个数字必备：房源量级【填】、意图路由准确率【填】、预约流程完成率【填】
