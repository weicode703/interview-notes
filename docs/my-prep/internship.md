## 电梯稿（30 秒，背熟）

> 实习在一家企业协作 SaaS 公司做 AI 应用开发，核心是给一个企业办公 AI 助手打地基。上层我负责制度问答场景：LangChain 搭 RAG 原型，审批和考勤制度文档切分、向量化、检索，回答强制带来源引用压制幻觉。更重要的产出是下层——给 Agent 的 Tool Calling 做数据底座：一套把任务数据自动同步过来的服务，覆盖 16 位高管和部门负责人的 98 项周期任务，变更 1 分钟内自动写入，替代了人工补录，整个实习周期稳定运行。可靠性上是事务性队列做幂等去重、指数退避加重试上限转死信、每日全量校准兜底——Agent 查到的数据永远是准的和新的。

## 高概率追问链（含参考答案）

### 一、受控 Agent Tool（差异化亮点）

**1. "受控"的边界具体怎么设计？为什么不让 Agent 自由调用？** ⭐3

参考答案：制度问答场景对错误零容忍，Agent 自由决策工具调用一旦幻觉就会查错数据误导用户。所以边界是三层：**工具层**只暴露任务查询这一个只读 Tool，没有写操作；**参数层**用 schema 约束（部门/时间范围/任务状态是枚举值，LLM 只能填槽不能自由发挥）；**执行层**参数校验失败直接拒绝并返回引导话术，不做模糊执行。一句话总结：LLM 负责"理解用户要什么"，取数的路径是写死的——把幻觉挡在数据之前。参考 [Agent 的安全执行与沙盒边界](/evaluation-deployment/agent-security-execution)。

**2. RAG 回答制度问题，怎么让用户敢信？来源引用怎么实现？** ⭐2

参考答案：检索时每个召回片段带文档 ID 和段落定位；生成时 prompt 要求"仅基于给定材料回答，并标注引用编号"；前端把编号渲染成可点击的原文出处。无法从材料回答的问题，直接说"制度文档里没有相关条款"，禁止模型自由发挥。这是对抗幻觉最硬的手段：**答案和证据绑定**。

### 二、数据 Pipeline 与可靠性（"1000+"必被质疑）

**3. 增量同步和定时全量校准，为什么两个都要？只用一个行不行？** ⭐3

参考答案：不行，两者解决的是不同问题。增量（Webhook 驱动）保实时，但它天然有**丢事件**的可能——推送时服务重启、网络抖动、对端限流丢弃，丢一次数据就永久不一致。定时全量校准是**对账**：周期性拉一遍最新状态覆盖本地，把增量阶段的任何丢失和乱序修正回来。增量管"快"，全量管"对"，生产级同步的标准双保险。

**4. 事件去重怎么做的？幂等怎么保证？** ⭐3

参考答案：Webhook 会重复推送（对端 at-least-once 语义）。去重键用**事件 ID**，落库加唯一约束——重复事件插入冲突直接跳过；处理侧用状态表记录"已处理"标记，处理逻辑本身用批量 upsert（按任务 ID 主键覆盖写），天然幂等：同一条事件处理三次和一次的结果一样。

**5. 失败重试和死信处理具体怎么做？重试参数怎么定的？** ⭐2

参考答案（简历数字：60s→3600s，最多 8 次）：指数退避——首次失败等 60 秒，之后按指数增长到上限 1 小时，最多重试 8 次；超过次数标记为**死信**不再阻塞队列，同时日志告警。参数依据：任务是低峰批处理场景，退避下限取分钟级避免风暴，上限 1 小时保证"一个工作日内仍有多次机会"，8 次上限让最坏情况的滞留时间可控（约一天）。死信不丢，修复诱因（比如字段映射规则变了）后可以人工重放。JSONL 日志按事件 ID 记全链路，排查时一条事件从入队到落库全程可追溯——要能讲一个真实案例【填：你排查过的某个具体问题】。

**6. 为什么用 SQLite 做持久化队列，不用 Redis 队列 / MQ？** ⭐2

参考答案（权衡 + 演进，和 AIWear 的 pgvector 同一答法框架）：当前数据量小（千条级），SQLite 零部署依赖、文件即数据库，而且**入队和处理可以在同一事务里保证原子性**——服务崩溃队列也不丢，这对可靠性需求是本质优势。边界：写入并发高或数据到百万级，SQLite 单写锁就是瓶颈，那时换 Redis Stream 或 MQ。我不否认它是轻量方案，但它是**当前规模下正确性最高、复杂度最低**的方案。

**7. Teambition OpenAPI 限流吗？Webhook 丢了怎么办？** ⭐2

参考答案：有频率限制，客户端做了【按你实际实现填：限速/退避重试】；Webhook 丢失靠定时全量校准兜底（回到第 3 题的逻辑）——所以单个通道不可靠没关系，机制上冗余了。

### 三、诚实面对"数据量小"

**8. "98 项任务"是不是量太小了？你真正学到的是什么？** ⭐3

参考答案（转化，不防御）：98 项不是我造的数字——是这个组织真实的任务规模（16 位高管与部门负责人的周报/月报/年报，我逐条统计过），同步服务解决的是"人肉补录会漏会错"的真实痛点，现在变更 1 分钟内自动写入。数据量由客户业务规模决定，不由我决定；我负责的是**机制的正确性**——去重、幂等、重试、死信、对账这套机制在 98 条和 98 万条时逻辑是同一套。如果数据 ×1000，我会改三处：队列换 Redis Stream、批量窗口加大、同步任务并行分片——说得出"什么会先坏、坏了怎么换"，比数据量本身更能说明工程能力。

**8b. 目标平台限制"禁止第三方直接新增行"，同步怎么继续工作？** ⭐2

参考答案：这是钉钉数据连接中心同步表的真实限制。设计**等待行轮询模式**：新任务的事件进不了写入流程时，任务留在本地等待队列，按固定间隔用任务 ID 反查目标行是否已由官方通道生成；等待期不计入失败次数（不是任务的错），超过等待上限（如 24 小时）才转死信，避免无限堆积。本质：把"平台约束"显式建模成一个队列状态，而不是当成错误。

**8c. 为什么 HS256 JWT 自己实现，不用现成库？** ⭐2

参考答案：项目约束是**纯标准库零第三方运行时依赖**（可移植性 + 交付面最小）。JWT 的核心就是 header.payload.signature 的 HMAC-SHA256 签名，几十行代码，自实现反而少一个依赖；同理 Webhook 验签也是 HMAC 比对。注意点主动说：签名比较必须**常量时间比较**防时序攻击、密钥走环境变量不入库不入日志。追问"你知道 JWE/RSA 吗"——知道，场景只需要对称签名验完整性，非对称是多方互信场景的事。
