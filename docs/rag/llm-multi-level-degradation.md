## 问题

RAG 问答深度依赖外部 LLM API。主模型限流、服务抖动甚至宕机时，整个问答功能就跟着不可用了吗？
多级降级链怎么设计？降级到什么程度是可以接受的底线？（简历项目：AIWear 的 qwen → OpenAI 兼容接口 → 本地拼装三级降级）

## 核心答案

- **降级链设计**：主模型（DashScope 流式）→ 备用模型（OpenAI 兼容接口，换 `base_url` 即可接任意供应商）→ 本地兜底（检索 Top-1 片段 + 引导话术拼装，不再调用任何模型）。

- **设计原则**：逐级降低"智能上限"，但保住"可用性下限"。本地兜底不再生成新内容、只返回召回片段原文——宁肯答得保守，不给模型编造的机会。

- **切换时机**：流式场景有个关键细节——必须在"尚未产出任何内容"时才能整体切换下一级；如果已经给用户吐了半截答案，中途切换会出现内容混杂，只能错误终止。

- **降级可感知**：降级状态通过响应/SSE 事件里的来源字段（如 `source: qwen / openai / fallback`）透出，前端可提示"当前为降级模式"，而不是让用户毫无感知地拿到低质量答案。

## 深度解析

- 追问点：本地兜底为什么返回检索片段而不是固定话术？——固定话术零信息量；检索片段至少可能命中答案，且"答案 = 证据原文"是幻觉最小的输出形态。

- 追问点：降级的最大隐患是什么？——`except Exception: pass` 式静默吞异常，用户毫无感知拿到降级内容，线上问题被掩盖。正确做法：记日志 + 事件标记 + 只在"零产出"时才降级。

- 追问点：重试和降级的关系？——瞬时错误（429 / 超时）先做有限次退避重试同一级，重试耗尽再降级，两者是配合关系不是替代关系。

- 常见误区：把降级做成"报错给用户"。C 端问答产品对可用性要求高，兜底答案虽保守但保住了体验；企业内部工具才可以接受直接报错。
