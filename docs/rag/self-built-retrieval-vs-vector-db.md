## 问题

项目里向量检索是自建的（Redis 存向量 + 内存算余弦），面试官必问：为什么不用 pgvector / Milvus / FAISS？
是不知道有这些方案，还是有意为之？数据量涨了怎么办？（简历项目：AIWear 的 Redis 用户级向量索引）

## 核心答案

- **规模分层的标准答法**：
  - **百到千级 chunk / 单用户几百条图片**：内存全量暴力计算余弦，毫秒级返回——自建就是最优解，引入向量库纯属增加运维面；
  - **万到十万级 / 需要过滤和混合检索**：迁 PostgreSQL + pgvector——应用库同库、事务一致、SQL 过滤天然支持，迁移成本最低；
  - **百万级以上 / 高 QPS 向量服务**：专用向量库（Milvus）或云服务——这时 ANN 索引（HNSW 等）才是刚需。

- **自建索引长什么样**：每个向量存为一个 JSON 记录（向量 + 元数据 + 描述），按用户 ID 建集合索引（SET）——检索时取该用户的 key 集、加载向量、内存算余弦排序取 TopK。按用户隔离天然做了数据分区。

- **答题框架（比结论更重要）**：当前规模下自建延迟与成本最优 + 我知道它的边界在哪 + 触发什么条件迁什么方案——展示的是**选型判断力**，不是"我只会这个"。

## 深度解析

- 追问点：暴力检索复杂度多少，什么时候成瓶颈？——O(N×d)，N 是向量数 d 是维度（如 512）；单用户千级毫秒级，全局几十万级就要秒级——这就是迁 ANN 的信号。

- 追问点：Redis 方案的隐性代价？——内存型存储成本、向量随元数据序列化在 JSON 里没有压缩、缺乏带过滤的检索（品类过滤要自己在应用层做）。这些"知道自建的短处"比夸它更重要。

- 追问点：pgvector 和 Milvus 的本质区别？——pgvector 是"数据库里加向量列 + 索引"，赢在事务和数据共库；Milvus 是专用引擎，赢在海量下的性能和分布式——量级和运维能力决定选择。

- 常见误区：简历写"自建向量检索"被质疑时慌着认错——正确姿态是承认它是**有边界的合理选择**，并能说出边界外的路线图。
