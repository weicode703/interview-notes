## 问题

讲一下 Agent 的 checkpoint 机制。它包含哪些内容？具体怎么实现？是不是所有情况都能回滚？

## 核心答案

**是什么**：在关键节点把执行状态落盘，进程崩溃、任务中断、审批暂停之后，从最近一次检查点继续，而不是从头开始。

**存什么（四类）**：

1. **对话历史**：消息序列、工具调用及其结果；
2. **任务规划**：已完成哪些、还剩哪些；
3. **文件系统状态**：改了哪些文件、改动内容（diff 或 git 状态）；
4. **进程状态**：正在跑的进程、后台任务。

**怎么实现（分两层）**：

- **会话层**：持久化对话、工具调用、结果，靠这些重建上下文；
- **文件层**：记录文件修改差异或 git 操作，用来恢复工作区；
- 落盘粒度按节点/步，带版本或时间戳，支持回放到某一步；存储一般用 PG / Redis / 对象存储，看 QPS 和体积。

**不能全回滚**：

- 外部副作用**不可逆**——邮件已经发出、支付已经扣款、第三方接口已经执行、消息已经推送；
- checkpoint 只能恢复「我们这边的状态」，恢复不了「外面已经发生的事实」。

所以正确做法是：**动作前记意图 + 幂等键**，恢复后先查外部状态（查到成功就补记结果，确认没执行才重试），而不是无脑重放。

## 深度解析

- **和 Human-in-the-Loop 的关系**：等待审批时把状态存进检查点、释放执行资源，审批结果回来后从检查点恢复——这是「不占着线程等一个人」的实现方式。
- **清理策略**：每次图执行都写一份状态，旧检查点会膨胀（数据库里就是一堆死元组），要有保留策略。
- **检测「恢复得对不对」**：测试必须覆盖「执行到一半杀进程 → 重启恢复」这条路径，只测正常流程的恢复是假的。
