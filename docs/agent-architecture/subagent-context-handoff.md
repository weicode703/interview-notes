## 问题

多 Agent 按什么粒度拆分？主 Agent 给子 Agent 传哪些上下文？怎么避免信息丢失和 token 膨胀？子 Agent 失败或超时怎么恢复？

## 核心答案

**一、拆分粒度看三件事**

- **任务粒度**：每个子 Agent 能独立交付一个完整结果（能自己验收，不依赖别人中途喂数据）；
- **权限粒度**：写操作范围不同就该拆开，只读的可以共享——同一条写权限给到多个 Agent 是事故源头；
- **失败粒度**：失败能隔离、中间结果能保留，别一个子任务挂了整条链重来。

**二、主 Agent 传四样东西**

1. **目标**：要解决什么问题，什么样算完成；
2. **背景**：相关需求、已经确认的结论、必须遵守的约束；
3. **范围**：仓库路径、相关文件、允许修改的位置；
4. **交付要求**：要什么证据（测试结果、日志、链接）、验证做到什么程度、还有哪些未解决问题。

**三、防信息丢失 / 防 token 膨胀**

- 控制输入：独立任务用**干净上下文 + 精简说明**，不要把父会话全文复制过去；
- 控制回传：子 Agent 只返回结论、必要证据和文件位置，不要贴大段原文；
- 需要细节时按路径回去取，而不是让子 Agent 复述一遍。

**四、失败或超时怎么恢复**

- 子任务状态持久化，保留已完成部分；
- 超时或报错时，把**标准化的错误信息**（做了什么、错在哪、还能不能继续）返回父会话，由父决定重试、换方案还是降级；
- 写操作用幂等键，超时先查执行状态，别直接重跑。

## 深度解析

- **两个典型坑**：传太少——子 Agent 靠猜需求，交付回来的东西方向就错了；传太多——上下文被无关信息占满，成本翻倍还更不专注。
- **边界判断标准**：子 Agent 失败时，父 Agent 能不能只凭回传信息判断「该重试还是该换方案」。能，说明交接设计合格；不能，说明回传缺了判断依据。
- **和单 Agent 的取舍**：拆开换来的是关注点分离和并行，代价是 token 翻倍和一致性变差——子任务之间真有依赖时，拆了反而更慢。
