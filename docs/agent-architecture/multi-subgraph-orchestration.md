## 问题

一个对话 Agent 同时承担推荐、预约、查询、闲聊四类业务，全部塞一张图里会怎样？
按什么原则拆子图？主图和子图怎么分工？跨子图的数据（用户偏好）怎么共享？（简历项目：智居 Agent 的"单入口、多子图"）

## 核心答案

- **为什么不混一张图**：四类业务的状态结构完全不同——推荐围绕"查询条件→检索→排序"，预约围绕"字段收集→校验→出工单"，混在一个 State 里字段互相污染、条件边爆炸、每类业务的提示词互相稀释。

- **拆分原则（三条）**：①**状态结构差异**是第一判据（各业务要维护的字段集不同就拆）；②**流程可枚举**的业务适合状态机子图，LLM 只在节点内做理解和生成；③**职责隔离**——子图改版互不影响，单个子图的提示词复杂度可控。

- **主图只做两件事**：意图识别（结构化输出分类到 N 个业务之一）+ 路由。主图不写业务逻辑，业务演进不动主图。

- **跨子图共享数据**：用 LangGraph Store 按用户命名空间存长期数据（预算偏好、预约记录），任何子图都能读写——**会话内状态归各子图，跨会话数据归 Store**；偏好更新用区间放宽合并（新下限更低/新上限更高则更新）。

## 深度解析

- 追问点：这和 Multi-Agent 有什么区别？——子图拆分是**一个应用的模块化**（仍是单 Agent、单一对话线程）；Multi-Agent 是多个角色/多个模型的协作编排。前者解决复杂度，后者解决分工。

- 追问点：子图状态怎么防串味？——流程结束强制清空业务字段（如预约的标题/手机号），否则下一轮对话误入预约流程会复用旧状态重复下单；这就是"状态清理"要在 finalize 节点显式做的原因。

- 追问点：业务校验放哪层？——跨业务的（预约房源必须来自本会话推荐结果）放主图或公共节点；业务内的（手机号格式）放子图。判断标准：这个规则违约时需要谁来回滚状态。

- 延伸：人机交互中断在子图场景怎么统一收敛——见 [子图 Interrupt 冒泡与主图网关模式](/frameworks/langgraph-subgraph-interrupt-gateway)，两题合起来是这个架构的完整版。
