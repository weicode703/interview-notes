## 问题

几个子 Agent 给出冲突结论，父 Agent 具体怎么处理？为什么不能只靠投票？

## 核心答案

**处理顺序（四步）**：

1. **定位冲突点**：把「哪里不一致」说清楚——是事实冲突（数不一样）、口径冲突（定义不同），还是范围冲突（各答各的）；
2. **要求补证据**：让每个子 Agent 给出依据（引用、日志、行号、数据来源），没有证据的结论直接降权；
3. **父 Agent 复核**：自己调工具核验，或重跑相关子任务（换输入、换工具再试一次）；
4. **仍然定不了就升级人工**，别硬选一个。

**为什么投票不可靠**：

- 子 Agent 往往是**同一个模型、同一批资料**，错会错得一样——多数一致只说明「同源」，不说明「正确」；
- 判断还容易受位置、长度、表述自信度影响（和 LLM-as-Judge 的偏差同源）；
- 真正的分歧常常不在结论，而在底层数据或口径——投票只会把错误口径选成「共识」。

**什么时候投票有用**：子 Agent 彼此独立（不同模型、不同资料来源、不同工具路径），且问题本身有可判定的对错。这时多路一致才有信息量。

## 深度解析

- **更可靠的裁决依据是可验证的事实**：跑一次测试、查一次数据库、对齐一次时间线，比数票强得多。
- **冲突本身是信号**：多数冲突暴露的是上游问题——需求没写清、口径没统一、知识库有过期内容。修上游比在下游裁决划算。
- **落地建议**：在父 Agent 的协议里固定「结论必须带证据」，让冲突在产生时就可裁决，而不是等汇总时才发现对不上。
