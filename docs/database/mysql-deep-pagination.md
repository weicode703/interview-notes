## 问题

`SELECT * FROM orders ORDER BY id LIMIT 1000000, 20` 要跑好几秒，前几页却很快。
深分页为什么慢？有哪几种优化姿势？

## 核心答案

- **为什么慢**：`LIMIT 1000000, 20` 的真实执行是**取出前 1000020 行再丢掉前 100 万行**——回表/扫描成本全花在被丢弃的行上；偏移量越大越慢，这是语法语义决定的。

- **三种解法**：
  1. **游标分页（最优）**：记住上一页最后一条的排序值（`WHERE id > 上页最后id LIMIT 20`）——每页都只扫 20 行；代价是不能跳页，只能顺序翻（信息流/加载更多的标准做法）；
  2. **延迟关联**：先用覆盖索引把目标主键查出来，再回表拿整行——`SELECT * FROM orders JOIN (SELECT id FROM orders ORDER BY id LIMIT 1000000, 20) t USING(id)`，省掉 100 万次回表；
  3. **限制产品侧**：真·跳页需求禁止翻超过 N 页（百度也只给 76 页），或走搜索引擎/ES。

## 深度解析

- 追问点：为什么延迟关联有用？——子查询只查 id 时可以走**覆盖索引**（索引里就有 id，不用回表）；扫 100 万个主键值比回表 100 次万整行便宜一个量级。

- 追问点：游标分页怎么处理排序字段重复？——排序键不唯一时游标会漏行/重行，要加第二排序字段（如 `id`）做联合游标：`(create_time, id) > (上页最后时间, 上页最后id)`。

- 追问点：和"索引失效"有什么关系？——深分页的 SQL 索引往往没失效（还是走主键/二级索引），慢在被丢弃的扫描量——先确认慢在哪，别瞎建索引。

- 常见误区：`LIMIT 1000000, 20` 写成 `BETWEEN 1000000 AND 1000020`——LIMIT 是行偏移不是 ID 范围，中间有删除就不对。
