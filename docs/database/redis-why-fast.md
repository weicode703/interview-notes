## 问题

Redis 单线程为什么还能 10 万+ QPS？瓶颈在哪？
Redis 6.0 又引入多线程是为什么？不是说单线程就够吗？

## 核心答案

- **快的四个原因**：
  1. **纯内存**操作（对比磁盘数据库，快 2-3 个数量级）；
  2. **IO 多路复用**（epoll）：单线程同时监听成千上万个连接，谁的请求就绪处理谁，不阻塞等待；
  3. **单线程无锁**：没有线程上下文切换和锁竞争，命令串行执行天然原子；
  4. **高效数据结构**：SDS、跳表、压缩列表等按场景特化。

- **瓶颈不在 CPU 在内存和网络**：命令执行是内存速度（微秒级），慢在网络 IO 的读写——所以 6.0 的多线程只用在**网络 IO 读写和协议解析**上，**命令执行仍然是单线程**（保住原子性）。

- **单线程的代价要主动说**：任何一条慢命令会阻塞所有请求——`keys *`、大 key 的 `del`、`hgetall` 大 Hash 都是危险命令（用 `scan`、`unlink`、`hscan` 替代）。

## 深度解析

- 追问点：单线程怎么保证原子性？——命令队列串行执行，天然不需要锁；要原子性组合操作用 MULTI/Lua 脚本。

- 追问点：和 Memcached 的区别？——MC 是多线程 + 只支持简单 KV；Redis 是单线程 + 丰富数据结构 + 持久化 + 集群方案，定位不同。

- 追问点：和 Python 的 GIL 像不像？——都是"单执行流"，但成因不同：GIL 是解释器内存管理的限制，Redis 是刻意设计（内存操作足够快，省掉锁开销）。

- 延伸：正式答"为什么快"最好带上边界——数据全在内存的成本、单机容量上限，以及持久化（fork 子进程）带来的延迟毛刺。
