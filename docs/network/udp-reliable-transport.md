## 问题

UDP 不保证送达、不保证顺序、不保证不重复。如果业务必须用 UDP（低延迟场景：实时音视频、游戏、QUIC），
怎么在应用层把它做成"可靠"的？

## 核心答案

- **思路：把 TCP 在传输层干的事搬到应用层重做一遍**——

  1. **序号**：每个包打编号，接收方据此**去重**（丢弃重复包）和**检测乱序**；
  2. **确认应答**：接收方回 ACK，发送方维护"已确认/未确认"集合；
  3. **超时重传**：发出后启动定时器，超时未 ACK 就重传；RTT 自适应调整超时阈值；
  4. **流量控制**：接收方通告缓冲区余量，发送方限速；
  5. **拥塞控制**：慢启动/拥塞避免，探测网络容量（可选——实时场景宁可丢帧也不排队）。

- **现实参照**：QUIC（HTTP/3 底座）就是"UDP 之上实现可靠传输 + 多路复用 + 加密"的工业级范例；RTP/RTCP 则是"只做部分可靠"（允许丢帧）的另一个方向的例子。

## 深度解析

- 追问点：为什么有了 TCP 还要 UDP 上做可靠？——TCP 的队头阻塞（一个包丢了，后面的数据都得等）、连接迁移（换网络断连）等设计惯性在弱网/移动场景代价大；QUIC 在应用层实现就能绕开这些问题。

- 追问点：实时音视频为什么"不可靠"反而更好？——丢一帧画面无所谓，但为了补齐这一帧让所有后续帧排队（TCP 语义），直播就卡住了——**延迟敏感业务选择部分可靠**。

- 常见误区：答成"UDP 加个重传就行了"——没有序号就分不清"没收到"和"收到了但乱序"，五个组件是一个整体。
