## 问题

RAG 问答要支持连续追问（"那冬天呢？"依赖上一轮语境），但把全部历史塞进 Prompt 又贵又慢。
多轮记忆的常规设计是什么？滑动窗口取最近 N 条的 N 怎么定？会话本身怎么管理？（简历项目：AIWear 的 8 条短期记忆 + 会话管理）

## 核心答案

- **三层结构**：①**短期记忆**——只取最近 N 条消息（如 8 条）拼进 Prompt，提供"指代消解"所需的最近语境；②**会话持久化**——全部消息按会话 ID 落库（PostgreSQL），支持会话列表、切换、回看、删除；③**会话元信息**——用首条问题自动生成标题（截断前若干字），方便用户在多会话间定位。

- **N 怎么定**：三个约束取交集——token 预算（N 条 × 平均长度 ≤ 给历史的预算）、相关性（用户追问通常只依赖最近 2-3 轮）、成本（每轮都付历史的钱）。经验起点 6-10 条，靠观察"指代丢失"的 case 调整。

- **检索与记忆的分工**：历史管"用户说过什么"（短期窗口就够），知识库管"领域知识"（每次检索 Top-K）——追问场景里把窗口内历史和检索片段一起拼进 Prompt，模型才能答"那冬天呢？"。

## 深度解析

- 追问点：窗口外的历史永久丢了吗？——对生成是丢了（不在 Prompt 里），但库里全量保存；长会话的改进方向是**滚动摘要**：窗口滑出时把旧消息压缩成摘要替代原文。

- 追问点：为什么不用向量检索历史消息？——可以（按当前问题检索相关历史轮次），适合超长会话；短会话下滑动窗口更简单且不引入检索误差，规模上来了再演进。

- 追问点：多会话之间要隔离什么？——用户权限（只能访问自己的会话）、状态（切换会话时上下文整体切换，不能串味）；会话删除要级联删消息。

- 常见误区：把"记忆"等同于"全部历史拼 Prompt"——成本随轮数线性涨、长上下文还有 lost-in-the-middle 退化；记忆设计的本质是**分层取舍**：热的进窗口，温的做摘要，冷的只存库。
