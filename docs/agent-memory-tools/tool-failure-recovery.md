## 问题

工具调用失败了怎么办？哪些错误可以重试、哪些不能？外部操作已经成功、但还没写进 checkpoint 就宕机，怎么避免重复执行？

## 核心答案

**第一步永远是分类，不是重试**：

| 错误类型 | 典型表现 | 处理 |
| --- | --- | --- |
| 临时故障 | 超时、限流 429、5xx、网络抖动 | 有限重试 + 指数退避 + 抖动 |
| 确定性错误 | 参数非法、404、403、业务校验不通过 | 不重试，把错误回填给模型改参数或换工具 |
| 不可逆副作用 | 支付、发消息、建单、删数据 | 先查状态，再决定 |

**写操作的三步法**（这是这题的核心）：

1. **执行前记操作 ID**：生成幂等键（业务唯一键或本次操作 ID），随请求带到下游；
2. **下游按幂等键去重**：重复请求落到唯一索引上直接被拒或返回原结果；
3. **恢复后先查状态**：查得到「已成功」就补记结果，确认「未执行」才重试。**顺序不能反**——先重试再查，就是重复扣款/重复发消息。

**错误也是上下文**：工具错误要按统一格式回填（错误码、消息、是否可重试），模型才能自己改参数或换路径。只回一句「失败了」，模型只能瞎猜。

**重试要有上限**：次数上限 + 总时长预算，超限进死信或转人工，别让一个工具把整个 loop 拖死。

## 深度解析

- **幂等键放哪**：放在请求头或参数里带到下游，下游落库时建唯一索引；跨系统的场景要能查（对账接口、状态查询接口），否则「先查状态」这一步做不到。
- **和 checkpoint 的关系**：检查点记录的是「已经发出的调用」，重启后第一件事是对齐外部状态，再决定补发还是跳过——不能只看本地记录就重放。
- **典型事故**：给「创建订单」加自动重试，接口超时但下游其实成功了，重试直接建出两单。所以写操作的重试必须挂在幂等键上，而读操作可以随便重。
- **和熔断的关系**：同一个工具连续失败，应该短暂停用（熔断），避免整个 agent 在坏工具上空转，冷却后再探测恢复。
