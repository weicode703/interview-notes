## 问题

一次要调多个工具时，什么时候并行、什么时候必须串行？并发怎么限制？工具定义里除了名称、描述、参数，还应该声明哪些执行属性？

## 核心答案

**并行 vs 串行的判断只有两条**：

- 并行：调用之间**无数据依赖**，且**无写冲突**（只读，互不影响）；
- 串行：后一步的参数依赖前一步的结果，或者两个调用会改同一份资源。

**并发怎么限**：由执行层限，不由模型自觉。

- 用队列 / 信号量限制同时在跑的工具数；
- 每个调用带超时，超时就当失败进入错误处理；
- 按调用 ID 关联结果——并行出去、乱序回来也能正确配对；
- 有全局预算（步数、总耗时、总 token），任何一项超限就熔断。

**工具定义里该有的执行属性**（这块最容易被漏掉）：

| 属性 | 作用 |
| --- | --- |
| 读写范围 | 决定能不能并行、要不要审批 |
| 所需权限 | 执行前校验，不靠模型自觉 |
| 是否幂等 | 决定失败后能不能重试 |
| 能否并行 | 调度器直接读，不用猜 |
| 超时与成本 | 长任务单独排队，贵工具单独计量 |
| 是否需要人工确认 | 高风险操作的开关 |

这些属性写进工具定义，调度器就能自动决定「并行还是排队、重试还是查状态、直接跑还是挂起等审批」，而不是靠模型临场判断。

**为什么工具结果要统一格式**：并行返回时靠调用 ID 才能正确配对；错误码、超时语义统一，日志和重试才好做；格式统一了，上下文压缩时才能按同一种结构做摘要。

## 深度解析

- **一个典型翻车**：模型并行发出两个「改同一条记录」的调用，后写的把先写的覆盖了，还看不出错——执行层必须在派发前做资源冲突检测，冲突就强制串行或直接拒绝。
- **和审批的结合**：需要人工确认的调用先挂起，其余并行跑；审批回来后单独恢复，不用整批重跑。
- **别把并发交给模型**：模型只会说「我要同时调这几个」，至于真开几个线程、超时多少、失败了怎么退，都是执行层的事。
