## 问题

工具数量到了几十上百个，全塞进上下文会出什么问题？怎么保证模型精准选工具、不乱调？

## 核心答案

**先承认问题**：工具定义本身就吃 token（上百个工具轻松上万 token），更麻烦的是准确率——相似工具互相干扰，模型会选「差不多但不是这个」的那个，然后参数跟着一起错。

**四种解法，通常组合用**：

1. **工具检索**：工具名 + 描述做 embedding，按当前用户 query 召回 Top-K 工具再放进上下文。配套要做好召回失败兜底（回落到分组或全量），工具描述要写清「什么时候该用我」，否则向量也对不准。
2. **分层路由**：先选业务域（用分组配置或轻量分类器/小模型），再在域内选具体工具。工具上百个时，先选组通常比一次选准容易得多。
3. **渐进式披露**：先只给「工具名 + 一句话」，模型表示要用某个工具再加载完整 schema。省 token，也减少干扰。
4. **收敛工具集**：合并重复工具，一个动作一个工具，别留 `createOrderV1` / `createOrderV2` 并存。工具越少越准，这是最便宜的一招。

## 深度解析

- **怎么验证有没有变准**：建一份「这句话该调哪个工具」的标注集，量化 tool selection accuracy；每次改描述、改分组、加工具后跑回归，否则只能凭感觉。
- **两个常见坑**：
  - 检索把「参数相关但动作不对」的工具捞进来（查订单 vs 查退款），要靠描述里明确「动作 + 触发条件」来区分；
  - 分组粒度过细，路由两跳都可能错，错误还会叠加。
- **为什么不能只靠模型自己筛**：模型没有「工具存在性」的先验，看不到就不会调；看到了太多又会选错。所以是工程层给候选集、模型在候选集里决策。
