## 问题

用 `with_structured_output` / JSON Schema 已经能约束 LLM 的输出格式了，为什么线上抽取还是会出错——用户没说城市，模型自己填了一个？
格式正确就等于内容可信吗？工程上怎么把"模型说抽到了"变成"确实抽到了"？（简历项目：智居 Agent 的反幻觉双保险）

## 核心答案

- **结构化输出的能力边界**：Schema 只能约束"形状"（字段名、类型、枚举值），约束不了"事实"——模型完全可能礼貌地编：用户没提预算，它按常识填 3000。格式校验通过 ≠ 内容为真。

- **确定性校验（第二保）**：对关键字段叠一层代码校验，原则是**"模型说有不算，原文命中才算"**：
  - 城市字段：用户原话必须命中常见城市名词表，或匹配"XX市/区/县"后缀正则；
  - 金额字段：必须命中"数字＋元/k/千"的金额模式；
  - 方向歧义：用"以上/以下/以内"等方向词判定区间该保留哪个边界（"3000 以下"→ 只留上限）；
  - 校验不通过的字段**直接丢弃置空**，走追问补全或默认值，绝不带病进入下游。

- **为什么两道都要**：只靠结构化，挡不住"合理编造"；只靠正则，理解不了自然语言。**LLM 管理解、规则管事实**——概率系统负责从对话里识别意图，确定性系统负责核对证据。

## 深度解析

- 追问点：为什么丢弃而不是让模型重试？——模型在没有证据时的重试大概率还是编（同一个分布再采样）；置空＋追问是在向用户要证据，一步到位。

- 追问点：这套方法适用于所有抽取场景吗？——不。适合"字段可枚举/可模式化"的场景（地名、金额、日期、手机号）；开放域字段（用户描述的偏好风格）没法正则化，只能靠结构化约束 + 温度调低。

- 追问点：和 RAG 的 grounding 什么关系？——同一个思想的两种落法：RAG 是"答案必须有检索证据"，这里是"抽取必须有原文证据"，本质都是**把 LLM 的输出锚定到可验证的事实源**。

- 常见误区：以为加了 Schema / JSON Mode 就"没有幻觉了"——幻觉从"格式错误"变成了"格式正确的编造"，更隐蔽、危害更大。
